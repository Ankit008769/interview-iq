# InterviewIQ — AI Mock Interview Coach (MERN starter)

A portfolio-level MERN application for realistic, role-specific mock interviews. This repository contains a **working application scaffold** for signup, login, interview configuration, text-based question/answer sessions, feedback, dashboard and history. Questions can be read aloud, and AI interviews accept spoken answers that are transcribed for review when a transcription model is configured ([voice answers](docs/VOICE_ANSWERS.md)). AI interviews can be tailored to a pasted resume or job description, with the source line shown under each tailored question ([resume and JD grounding](docs/RESUME_JD_GROUNDING.md)). Voice answers can be transcribed on the server by a local Whisper model ([voice answers](docs/VOICE_ANSWERS.md)) and get optional pace and filler-word feedback, and behavioral answers can be checked for STAR structure; neither affects scores ([delivery and STAR](docs/DELIVERY_AND_STAR.md)). AI interviews can be held in English, Hindi or Hinglish (beta; [languages](docs/LANGUAGES.md)). A coding lab runs JavaScript, TypeScript, Python, Java, C++ and SQL solutions against hidden tests in a separate sandboxed runner, then the AI interviewer asks about the approach and reviews it; test results never come from the AI ([coding lab](docs/CODING_LAB.md)). A system-design board (Excalidraw) reads the candidate's diagram as components and connections, checks capacity estimates arithmetically, and the AI interviewer changes constraints and reviews the design against a trade-off rubric ([system design](docs/SYSTEM_DESIGN.md)). Candidates can upload a project's code as a zip: secrets are removed before it is saved, it is indexed with tree-sitter, resume claims are checked against it, and a project-defense interview asks about specific files and functions ([project defense](docs/PROJECT_DEFENSE.md)). A Learn page keeps an estimate and uncertainty for 20 skills, schedules spaced retests and picks one short drill a day, focused by an optional interview date; setup offers product, IT services and startup interview styles ([adaptive learning](docs/ADAPTIVE_LEARNING.md)). Colleges' placement offices can run cohorts on a Campus page: students join with a code after agreeing to what is shared, staff import rosters from CSV, set interview, coding and design assignments or drive-preparation packs, and follow a placement-readiness index with CSV export ([campus](docs/CAMPUS.md)). Optional camera practice gives on-device framing and eye-line tips (MediaPipe in the browser, no emotion inference) and records each answer for self-review on that device only, and an optional drawn interviewer avatar moves while questions are read aloud ([video self-review](docs/VIDEO_SELF_REVIEW.md)). Plans, payments through Razorpay and Stripe hosted pages, GST invoices, coupons and referrals are built but switched off during the free beta ([billing](docs/BILLING.md)). Candidates can share a signed, revocable skill passport, a W3C Verifiable Credential labelled as a practice record and not a hiring score ([skill passport](docs/SKILL_PASSPORT.md)). Questions and scores can come from open models running locally through Ollama, with nothing sent to an outside AI company ([local models](docs/LOCAL_MODELS.md)). File uploads and real-time voice are *planned*, not implemented in this version.

## Current flow

**Register/login → Dashboard → Choose role/type/difficulty/topic → Start session → Answer 2–5 questions → AI or practice-mode feedback → Review history**.

- **AI mode** when `OPENAI_API_KEY` is configured: questions, context-aware follow-ups and feedback are generated by an LLM using schema-constrained Responses API output.
- **Practice mode** without API key: questions come from a 108-question bank tagged by topic and difficulty, chosen so a session never repeats a question and returning users get questions they have not seen recently ([question bank](docs/QUESTION_BANK.md)). Feedback clearly states that it does **not** score technical quality. Practice mode never pretends to be AI.

## Requirements

- Node.js 20.19+ (22+ recommended)
- npm
- A running MongoDB database (local, container or MongoDB Atlas)
- Optional: OpenAI API key with access to the model set in `AI_MODEL`

## Run locally

1. Start MongoDB, e.g. `docker compose up -d` from this folder (requires Docker Desktop), or start your local mongod service. The sample Docker Compose binds only to localhost.
2. Copy `server/.env.example` to `server/.env`. Set `MONGODB_URI` if needed, and set a **new long random** `JWT_SECRET`. Optionally add `OPENAI_API_KEY`.
3. Open a terminal for the backend:

   ```bash
   cd server
   npm install
   npm run dev
   ```

4. Open a *second terminal* for the frontend:

   ```bash
   cd client
   npm install
   npm run dev
   ```

5. Open **http://localhost:5173**; sign up and create a mock interview. Backend health check: **http://localhost:5000/api/health**.

**Windows PowerShell example** (from the project root):

```powershell
Copy-Item server/.env.example server/.env
# Edit server/.env with your MongoDB URI and new JWT secret.
```

## Tech stack

React + TypeScript + Vite + Lucide React; Node.js + Express + TypeScript; MongoDB + Mongoose; HTTP-only revocable opaque session cookie; Zod input checks; optional OpenAI Responses API with structured output. Styles are custom CSS with responsive layouts.

All interview endpoints require authentication and enforce interview ownership. Submission checks prevent duplicate additions to the same question.

Answer requests must include `answer`, a zero-based `questionIndex`, and a stable
`submissionId` for that question. Retry the same payload with the same ID after a
network failure. Replaying a saved submission returns the current interview with
`replayed: true`; reusing an ID with different content or submitting a stale
question returns 409. Deploy client and API updates together for this contract.

New answers return **202 Accepted** after the answer and pending job are saved
atomically. Poll `GET /api/interviews/:id` while `processingState` is `queued` or
`processing`. `ready` means the next question or final feedback is available;
`failed` exposes a retry action. Retry processing with `POST /api/interviews/:id/retry`
without resending an answer. An exact answer replay returns 200 and the current
state, including when processing is still pending.

The API process runs a MongoDB-backed worker on startup. It makes up to three
automatic attempts, backs off between provider failures, and reclaims work after
a two-minute worker lease expires. A lease token prevents an obsolete worker from
overwriting a newer result. Accepted answers survive API restarts; initial question
creation still requires generation to succeed. This provides idempotent database
effects, not exactly-once provider billing: an expired attempt can cause another
provider call. See `docs/ANSWER_RECOVERY.md` for the state transitions and limits.

## Evaluator calibration

AI scores are labelled uncalibrated until a human panel's ratings show the AI judge
agrees with experts. `npm run calibration` in `server` builds blind rating sheets, runs
the AI judge on a calibration item set, builds an evidence audit sheet and produces an
agreement report with the Phase A gates. See [calibration](docs/CALIBRATION.md) and the
[rater guide](docs/RATER_GUIDE.md).

## Development checks

Dependencies are locked separately for client and server. Run `npm ci` in each
directory for a reproducible installation, then `npm run build` in each directory.
Run `npm test` in `server` for MongoDB-backed API regression tests. Tests use an
isolated temporary database and practice mode; they need no API key or existing
MongoDB service. The first test run downloads a MongoDB binary and requires network
access. GitHub Actions runs both builds and these API tests.

The tests cover session completion, delayed answer retries, conflicting and
concurrent submissions, authentication/ownership, lifetime dashboard totals,
provider failures, restart recovery, lease fencing and final-feedback recovery.

For browser tests, build `client` first, then run `npx playwright install chromium`
and `npm run test:e2e` from `server`. The test fixture serves the built client and
an isolated database at `http://127.0.0.1:5101`. Port 5101 must be available.
These tests cover reload/reconnection, processing retry, a lost save acknowledgement,
the completed practice flow, and failed/successful logout. Test-only control routes
exist solely in `server/e2e/fixture.ts`, which is excluded from the production build.

## Security and production considerations

- API keys stay on the Express server. Never use `VITE_OPENAI_API_KEY`.
- Passwords use bcrypt hashing and session tokens are held in HTTP-only cookies. JWT_SECRET (retained configuration name for auth-limit IP hashing) must be long and random.
- Cookie handling uses `SameSite=Lax`; deploy frontend and API under one site (e.g. `yourdomain.com` and same-origin `/api` proxy). If deploying across distinct sites, redesign cookie/CSRF handling carefully rather than simply switching to `SameSite=None`.
- For public production use: configure live email, stronger abuse prevention, accessible UX review, independently replicated deletion receipts and full operational hardening.
- The interview evaluation is **coaching feedback**, not an objective measure of employability or a hiring decision.
- User content is handled as untrusted data in prompts and model output is parsed through a defined schema.

## Implementation phases

Phase A has started with a replaceable model-provider boundary and evidence-based
scorecards. Technical, Behavioral and HR reports use versioned rubrics, 0–5 criteria,
verified answer quotes and explicit insufficient-evidence states. Practice reports
show the rubric for self-review without invented scores. See
[the API-first Phase A plan and configuration](docs/PHASE_A_API_FIRST.md).

Phase 0 delivers persistence/recovery, history pagination, account error handling,
shared quotas, production configuration, 25 backend tests and 9 Chromium tests.
Private staging runs on Google Cloud; see [staging operations](docs/GOOGLE_CLOUD_STAGING.md).

Next phases are credible text coaching with versioned rubrics and evaluation data;
resume/job-description grounding; voice; an isolated coding lab; adaptive learning;
and private beta/launch readiness. Assistant planning notes remain outside this repo.

[answer recovery](docs/ANSWER_RECOVERY.md), and
